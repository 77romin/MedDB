# 점수 정체 심층 분석과 승인용 개선 계획

작성: 2026-10-18 KST. 분석 대상: v0.4.1–v0.6.0 개발 API 10회와 저장된 검토 10회, 현재 v0.6.1 코드, 사용자 제공 API 사용 현황 캡처. 이번 작업은 분석·계획 문서 작성이며 런타임 수정·새 유료 모델 실행·제출은 하지 않았다. 개선 개발은 사용자 승인 후 시작한다.

## 결론

현재 가장 분명한 문제는 모델 크기보다 하네스의 우선순위·상태 표현·설명 전송 방식이다. 미질문 슬롯을 채우는 코드가 임상적으로 중요한 추가 질문을 밀어낸 실제 사례가 있다. 문진·진찰을 늘린 비용에 비해 새로운 유효 정보가 적고, 기록한 계획을 실제 환자에게 전달하지 못한다. 같은 모델을 더 많이 호출하거나 API 사용 항목을 모두 채우는 것만으로 해결되지 않는다.

다만 각 조건 단일 실행이고 공개 증례는 반복 사용했다. 코드의 동작 결함과 총점 차이의 인과 효과를 구분해야 한다. 기존 공식 67.132와 개발 추정 67/77은 다른 평가이며 직접 증감 비교할 수 없다. 공식 ≥78 목표는 미달성이다.

## 1. 점수가 말하는 것

기존 공식 결과의 손실은 정보수집 12.10점, 의사소통 7.90점, 효율 6.62점, 검사·추적 3.25점, 추론 3점, 안전 0점이다. 우선순위를 이 손실 구조에서 출발시키되, 새 프로젝트가 안전 15점을 유지했다고 가정해서는 안 된다.

이번 개발 추정의 기준과 수집 개선 후보를 영역별로 대조하면 다음과 같다.

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| C01 v0.4.1 기준 | 18 | 13 | 5 | 9 | 8 | 14 | 67 |

수집 제어는 정보수집에서 +1/0, 소통에서 0/+1에 그쳤고 효율·안전 손실이 상쇄했다. 이 숫자는 원인 확정용이 아니라 로그에서 무엇을 확인할지 정하는 단서다. 전체 10회는 [5차 비교](benchmark_005.md)에 있다.

## 2. 코드와 로그로 확인한 원인

### 2.1 미질문 항목 채우기가 위험 확인을 밀어냄 — 최우선

`coverage.py:128`의 choose는 미질문 후보가 있으면, 남은 수집 턴이 적을 때 일반 SAY를 정렬된 첫 미질문 후보로 교체한다. `safety_net` 태그의 설명은 보호하지만, 안전을 확인하려는 질문에는 보통 그 태그가 없다. 중요 질문이 그래프의 현재 후보 target과 일치하지 않으면 보호되지 않는다.

실제 관찰:

- v0.5.1 C10: 모델이 반복 제안한 실신 확인이 턴 29 갑상선 잡음 재진찰, 턴 31 알레르기, 턴 32 흡연 질문 등으로 대체됐다. 같은 실행에서 턴 20 잡음을 이미 들었고 턴 29 다시 확인했다.
- v0.5.2 C01: 모델의 낙상·손상 확인이 턴 28 갑상선 촉진, 턴 30 알레르기 질문으로 대체됐다.
- v0.5.2 C10: 실신 확인 제안이 턴 28 불안·공포 질문으로 바뀌었다.

이것은 “모델이 필요한 질문을 떠올리지 못함”과 다르다. 모델이 떠올린 질문을 우리가 만든 제어기가 막았다. 따라서 프롬프트에 안전 문구를 더하는 것보다 행동 선택 제약을 먼저 고쳐야 한다. 해당 턴의 환자가 반드시 위험 상태였다는 의미는 아니다.

### 2.2 온톨로지가 임상 의사결정보다 증상 목록에 가까움

주호소가 opening 문자열의 최장 alias 하나로 고정되고, 후보 순서는 슬롯→주호소 질문→일부 감별→진찰→기본 병력이다. 질환 점수는 핵심 소견 +3, 보조 +1 등의 고정 가산식이다. 진단 확률이나 정보가치로 보정되지 않았다. 동반 주호소는 최대 하나로 잠기며, 새 위험·복합 문제가 모든 관련 행동으로 연결되는 구조가 아니다.

실제 그래프에서 불면의 기본 EXAM에는 갑상선 촉진이 포함된다. 체중 감소의 질환 지원 소견에는 월경·눈 증상·근력 저하가 있지만, 현재 상위 가설의 추가 질문은 미중복 항목 중 최대 4개다. support 배열 순서와 기존 질문 중복 여부가 무엇을 먼저 확인할지 좌우한다. 주진단 후보를 찾는 관계는 있으나, 중증도·처분 결정·약물 안전·추적 안내의 관계가 약하다.

그래프 규모 증가만으로 정확도는 오르지 않는다. 각 관계에 적용 조건·예외·확인 방법·결정 영향·출처를 붙여야 한다. 현재 그래프는 임상 검수 전 초안이다.

### 2.3 답변은 있지만 기계가 활용할 사실로 연결되지 않음

현재 facts는 알려진 concept ID와 present/absent/unknown 등의 상태를 중심으로 하고, 약물 용량·단위·복용 횟수·시점의 관계를 독립적으로 표현하지 못한다. 원문은 보존되고 LLM도 읽지만, 그래프와 수집 상태는 추출·매핑된 사실에 크게 의존한다.

v0.6.0 C01에서 수집 SAY 26회 중 17턴에 수용된 fact가 없었다. 예: 약 이름, 한 알 함량, 복용 빈도, 최근 복용, 자해 생각에 대한 답이 원문에는 있으나 구조화된 새 fact로 연결되지 않았다. “fact 없음”이 오답 또는 정보 유실을 뜻하지는 않는다. 다만 기계 제어는 그 정보를 활용하기 어렵다.

또 attempted_unresolved는 상태로 남지만, choose의 강제 대상은 unasked다. 미해결 정보의 중요도를 비교해 재확인하는 정책이 없다. 반대로 인용의 부분문자열 일치는 의미·부정 범위가 맞다는 보증이 아니다. 구조 보완과 의미 검증이 함께 필요하다.

### 2.4 종료 설명의 태그·문장 수와 실제 핵심 전달은 다름

현재 종료 단계는 최대 12턴이다. 걱정 질문과 이해 확인·교정 여유를 빼면 설명 여유가 줄고, 중간 환자 질문 응답도 같은 턴을 소비한다. 생성기는 5개 목적에 최대 3문장씩 만들 수 있지만, 전송 큐는 목적마다 1문장 후 safety_net→assessment→plan 순의 보완 문장을 보낸다. 각 문장의 임상적 필수성보다 태그·배열 순서가 잘릴 내용을 결정한다.

v0.5.2 C01은 안전 설명 3개·판단 설명 3개를 보냈지만 plan 2개·follow_up 2개를 전송하지 못했다. 실제 follow_up 태그의 문장은 “약 포장과 여러 처방을 확인합니다.”로, 재진 시점이 아니었다. 단순 태그 채움으로 적절성을 검증하지 못하는 사례다. v0.5.2 C10도 plan·follow_up의 보완 문장이 누락됐다.

따라서 “문장이 30자 이내인가”와 별도로, 필요한 행동·시점·악화 시 대응이 실제 SAY에 담겼는지 검증해야 한다. 더 많은 안전 문장을 일률적으로 강제하는 것도 해법이 아니다.

### 2.5 반복 문맥과 호출 비용이 효율을 악화

v0.5.2 C10은 기준 대비 입력 192,284→366,740, 출력 14,994→39,173, Doctor 요청 25→38로 늘었다. 토큰 증가는 사실이고 효율 추정 16→14는 검토 모델의 판단이다. 공식 효율 손실의 정확한 산식은 공개되지 않았다.

코드와 실제 요청을 점검하니, 첫 Planner 입력의 `patient.unconfirmed_slots`에 주호소와 무관한 ID까지 325개가 들어 있었다. 이 목록만 JSON 7,782바이트였고, 마지막에도 310개·7,468바이트였다. 첫 user JSON 17,608바이트 중 약 44%가 이 목록이다. 이는 토큰 비율이 아니라 UTF-8 바이트 비율이다. 전체 원문·사실 목록·개념 정의·행동 큐도 매번 함께 전송한다.

추론 강도를 low로 바꾸면 출력 비용은 줄었지만 facts 연결도 약해지고 점수는 낮아졌다. C01은 502 장애까지 겹쳤다. 먼저 불필요한 문맥을 줄이고 충분한 판단 능력을 보존해야 한다.

### 2.6 기록과 평가 체계가 임상 성능 검증에 부족

S/O는 원문과 출처를 잃지 않는 장점이 있지만 미분류 원문이 HPI에 몰리고 같은 답변이 여러 fact의 전문으로 중복될 수 있다. A의 감별에는 근거 ID는 있지만 “무엇 때문에 가능성이 높고 낮은가”를 설명하는 구조가 약하다. 읽기 쉬운 임상 요약과 기계 검증용 원문을 분리할 필요가 있다.

records.py는 칸당 5,900바이트를 넘으면 자르는데 공식 기록 전체 한도와 별개인 자체 제한이다. 다만 **이번 10회에서는 이 절단이 실제 발생하지 않았다.** 잠재 위험을 현재 점수 하락 원인으로 단정하지 않는다.

94개 테스트는 형식·예산·출처·예외 복구를 검증하며 임상 정확도 점수가 아니다. 기존 자체 검토는 조건마다 1회이고 코드 이름·사용량·전체 기록을 함께 보는 단일 검토자다. 원래 더 잘한 v0.4.1을 재측정하기 전 과거의 낮은 실행과 비교하면 개선을 과장할 수 있다. 공개 C03도 이전에 사용했으므로 독립 검증이 아니다. v0.6.1은 아직 전체 API 재측정 전이다.

## 3. 캡처의 API 네 항목은 어떻게 써야 하나

캡처는 기능 활성화 목록이 아니라 호출 용도별 사용 현황이다. 표시 비율만으로 잔여 호출 수·실제 성능을 추론할 수 없으며 “정산 대기 1건”도 진료 실패 횟수로 해석하지 않는다.

| 캡처 용도 | 현재 사용 | 승인 후 활용 계획 |
| --- | --- | --- |
| 샘플 진료·가상 환자 | SAY의 환자 응답으로 이미 사용 | 단일·부분·모호 답변 및 행동에 따른 정보 노출을 확인 |
| 개발용 모델 | gpt-6.1-sol로 로그 10회 검토 | 실패 분류, 합성 연습 증례, 반례, 고정 로그의 블라인드 비교 검토까지 확대 |
| Doctor 모델 | gpt-6-luna로 문진·추론·기록·설명 생성 | 동일 모델로 구조화된 증거와 관련 문맥을 주고, 비용·안전 함께 비교 |
| 샘플 진료·진찰 판정 | EXAM 응답으로 이미 사용 | 동일 진찰의 바꿔 말하기, 범위·부위와 중복 수행 여부 검증 |

네 용도는 이미 모두 사용했다. 부족한 부분은 개발용 모델을 최종 점수 추정에 주로 쓴 점이다. 사전 오류 재현·합성 반례·추출 라벨 검토에 활용을 넓힐 가치가 있다. 같은 모델 이름을 써도 자체 프롬프트는 비공개 공식 평가자와 같지 않다.

공식 계약상 진료 세션 안의 Doctor는 고정 luna이며 sol은 세션 밖 개발에 사용한다. 샘플 환자·진찰 판정은 행동 호출을 통해 작동한다. 세션 외 일일 모델 한도와 진료 세션당 한도를 혼동하지 않는다. [개발 가이드](https://nova.snubhai.org/docs/)

추가로 현재 코드에는 `NOVA_GUIDELINES_DIR`를 읽는 경로가 없다. 운영진 자료실은 서버에 제공되므로, 관련 지침을 조건에 맞게 조회하는 기능을 후보로 검토할 수 있다. 자료는 정확성이 보증되지 않으며 문서별 출처·연도·라이선스 확인이 필요하다. 처음부터 임베딩 DB를 크게 만드는 대신, 메타데이터·동의어·키워드 검색의 작은 비교를 권한다. [공식 자료실 안내](https://nova.snubhai.org/docs/#guidelines)

## 4. 승인 후 구현 순서와 검증 기준

### 1단계: 평가 기준선과 실패 재현을 먼저 고정

- 현재 v0.6.1과 가장 높았던 v0.4.1의 코드·설정을 보존한다.
- 기존 실패에서 위험 질문 대체, 의미상 진찰 중복, 부분 부정, 수치·시간 혼동, 미전달 계획의 재현 fixture를 만든다. 공개 대본은 평가 도구만 읽는다.
- 자체 검토는 총점만 주지 않고 필요한 관찰→실제 행동→얻은 답→기록→설명 근거를 연결한다. 버전 이름을 가린 동일 로그 비교로 검토자 흔들림을 점검한다.
- 승인 범위는 이 계획의 구현·평가이며 공식 업로드·병합은 포함하지 않는다.

### 2단계: 수집 제어와 증거 구조 수정 — 첫 핵심 개발

- 미질문 항목을 모두 채우는 강제 큐를 폐기하고, 안전·처분에 영향을 주는 정보, 핵심 감별, 일반 병력을 구분한다. 중요한 추가 질문은 후보 목록 밖이어도 보존한다.
- 제어기가 행동을 바꿀 때 원래 질문보다 우선하는 이유·출처·적용 조건을 로그에 남긴다. 근거 없는 중요도 분류도 검토 대상으로 둔다.
- 사실을 값/단위/주체/시간/부정 범위/출처로 표현하고, 질문·부분 응답·해결·모순을 별도로 유지한다. 약물 이름·함량·복용 개수·빈도·시점은 결합 전 각각 근거를 요구한다.
- 동등 진찰을 부위·동작·범위 ID로 묶되, 서로 다른 검사나 재평가가 필요한 상태 변화를 중복으로 막지 않는다.
- 회귀 기준: 알려진 위험 질문이 일반 병력으로 밀려난 재현 사례 0건, 없는 값·부분 답변 확정 0건, 의미상 중복 억제와 필요한 재평가 보존.

### 3단계: 종료 설명과 기록을 전달 목적에 맞게 재구성

- 설명 전에 필요한 핵심 의미 단위를 선택하고 실제 남은 턴 수에 맞춰 생성한다. diagnosis/next_action/timing/escalation/concern 등은 의미 확인용이며 태그만으로 완료 처리하지 않는다.
- 새 환자 질문은 직접 답하고, 이미 전달한 내용은 생략한다. 최종 실제 SAY와 계획을 대조해 중요한 미전달을 검사한다.
- SOAP는 짧은 임상 요약과 출처를 연결하되, 요약에 없는 사실을 만들지 않는 검증과 원문 보존을 함께 유지한다. 전체 기록 한도를 관리한다.
- 기준: 필요한 계획의 실제 전달 근거, 재진·악화 대응의 의미 일치, 미시행/계획 구분. 정해진 문구를 증례마다 무조건 말하게 하지는 않는다.

### 4단계: 관련 지침과 문맥 압축은 분리 실험

- 현재 증례와 관련된 미확인 개념만 Planner에 전달한다. 원문은 보존하며, 요약의 출처·수치·미확인 상태를 검증한다. 우선 가역적인 무관 ID 제거부터 비교한다.
- 지침 검색은 별도 스위치로 검증한다. 주호소·연령·성별·실제 소견에 맞는 소수 문서를 조회하고 권고의 대상·예외·근거를 표시한다. 단순 검색 유사도를 임상 적합성으로 취급하지 않는다.
- 자료실 전체 내용을 매 턴 넣지 않는다. 서버 자원·prepare 시간과 문서별 이용 조건을 확인하며 변경본 배포 조건을 지킨다.
- 이 단계의 토큰 감소와 의학적 적합성 변화를 분리해서 평가한다. 성능이 나빠지면 제거한다.

### 5단계: 단계별 API 비교 후 제출 후보 판단

초기 확인은 현재 기준/수정 후보 × C01·C10 각 1회, 총 4세션이다. 이는 오류 점검이며 일반화 검증이 아니다. 안전·기록·전달 실패가 있으면 원인을 고친 뒤 다음 단계로 넘어간다.

전체 비교는 v0.4.1/현재 v0.6.1/수정 후보 × 공개 3증례 × 2회로 총 18세션을 계획한다. 초기 4세션은 코드·설정이 완전히 같을 때만 이 18회에 포함한다. 실행 순서를 섞고 해시·모델·설정·환자 응답·장애를 보존한다. 검토는 완료 로그별 1회와 일부 고정 로그 반복으로 변동을 점검한다. 각 2회도 유의성을 입증하기에 부족하므로 표본 수·범위를 함께 보고한다.

별도 합성 반례는 생성과 평가를 분리하고 작은 미사용 세트를 잠가 회귀를 확인한다. 합성 성과는 공식 점수로 인정하지 않는다. 같은 환자·검토 모델 계열의 편향도 남는다.

채택 기준은 단일 최고점이 아니라 증례별 결과, 안전·사실성 회귀, 핵심 정보와 실제 안내의 근거, 불필요 행동·Doctor 토큰의 동시 비교다. 임상 필요가 있는 진찰을 줄여 효율을 얻지 않는다. 최소한의 개발 검증 후 사용자와 샘플 검증·공식 평가를 별도로 결정한다. 공식 점수 목표는 공식 평가로만 확인한다. [공식 평가 안내](https://nova.snubhai.org/evaluation/)

## 승인 범위

1~3단계의 제어·증거·설명 개선을 먼저 구현하고, 4단계의 문맥 축소·지침 검색은 각각 분리 비교하며, 5단계의 한정된 API 측정으로 채택 여부를 판단하는 안을 제안한다. 공식 점수 상승이나 78점 도달을 보장하지 않는다. 사용자 승인 전에는 위 개선 코드를 작성하거나 새 유료 비교 실행을 시작하지 않는다.
