# NOVA 온톨로지 기반 Doctor Agent 구현계획

작성 기준: 2026-10-18 KST. 현재 예선 Doctor: `openai/gpt-6-luna`.

이 문서는 구현 제안이다. 아직 임상 온톨로지·벡터 인덱스·에이전트 코드·성능 실험은 구축하거나 실행하지 않았다. 수치 목표는 초기 설계값이며 측정 후 조정한다. 공개되지 않은 채점 세부 항목이나 점수 향상을 확정적으로 가정하지 않는다.

## 1. 구현 방향과 우선순위

**권고안은 경량 임상 온톨로지, 환자별 증거 그래프, 근거 검색, 상태 기반 진료 제어, 역할별 프롬프트, 결정적 검증기를 하나의 하네스로 연결하는 것이다.**

정확도 개선의 경로를 네 가지로 분리한다.

1. 같은 증상을 다른 표현으로 말해도 동일 개념으로 연결한다.
2. 미확인·음성·과거력·현재 증상을 구별해 잘못된 진단 근거를 줄인다.
3. 감별진단에 필요한 질문과 진찰을 골라 실제 정보를 확보한다.
4. 확보한 사실을 빠짐없이 기록하고, 사실에 맞는 진단·계획·설명을 제출한다.

온톨로지 도입 자체가 진단 정확도를 보장하지 않는다. 관계 추출이 틀리면 오히려 오류가 전파되므로 baseline 대비 구성요소 제거 실험으로 채택 여부를 결정한다. 우선순위는 **실행 성공 → 증거 보존 → 필수 정보 확보 → 기록·설명 완결 → 추론·검색 고도화**다.

예선에서는 고정 모델을 파인튜닝하지 않고 상태·검색·프롬프트·정책을 개선한다. CPU 2코어·RAM 8GB·코드 ZIP 50MB, 외부 인터넷 차단을 전제로 한다. 최대 50턴, Doctor 200회, 준비 10분·진료 30분 안에 제출한다. [공식 규칙](https://nova.snubhai.org/rules/)

## 2. 전체 구성과 책임

| 모듈 | 입력과 출력 | 책임 |
| --- | --- | --- |
| ProtocolAdapter | SDK 세션·행동·응답 | 인증, ready, 요청 ID, 재시도, 턴·시간·토큰 회계 |
| FactExtractor | 시작 정보·환자 응답·진찰 결과 → 후보 사실 | 개념·부정·시간·수치·복용량 추출, 원문 범위 연결 |
| PatientState | 후보 사실 → 검증된 환자별 상태 | 관찰 사실·추론·모순·미확인 항목 분리 |
| ClinicalKnowledge | 정적 개념·관계·근거 문서 | 증상·질환·검사·약물·위험 신호·계획 관계 제공 |
| Retriever | 환자 사실·감별진단 → 근거 묶음 | 동의어 확장, 어휘 검색, 그래프 인접 탐색, 출처 반환 |
| Planner | 상태·후보 행동·근거·잔여 예산 → 행동 제안 | 다음 질문·진찰·설명·종료 선택 |
| ActionValidator | 행동 제안 → 실행 가능 행동 | 30자, 단일 항목, 단계, 중복, 근거 일치 검사 |
| NoteBuilder | 사실·판단·계획 → SOAP와 주진단 | 정확한 필드, 사실 인용, 누락·수치·음성 검증 |
| Evaluator | 실행 로그·기록 → 비교 보고서 | 영역별 대리지표, 오류 유형, 비용·시간·회귀 분석 |

런타임 순서: 정적 자산 준비 → ready → 시작 정보 정규화 → 사실·미확인 항목 갱신 → 필요한 경우 근거 검색 → 행동 선택·검증·실행 → 결과 반영 → 종료 전 환자 설명 → SOAP 검증 → DIAGNOSE 성공 확인.

이는 한 프로세스 안의 논리 모듈 구분이다. 역할마다 별도 에이전트를 항상 호출하지 않고, 보통 한 번의 Doctor 호출에 사실 갱신·다음 행동 제안을 묶는다.

## 3. 온톨로지 설계

### 3.1 정적 지식과 환자 사실 분리

정적 지식에는 `ClinicalConcept`, `Symptom`, `Disease`, `PhysicalExam`, `Test`, `Medication`, `RiskFactor`, `CareAction`, `GuidelineSource`를 둔다. 환자 사실에는 `Encounter`, `Observation`, `MedicationUse`, `Evidence`, `Hypothesis`, `CommunicationEvent`를 둔다.

동일 개념을 표현하는 동의어와, 특정 질환을 지지하는 임상 관계는 별도다. `is_a`, `same_meaning_as`, `supports`, `argues_against`, `assessed_by`, `requires_clarification`, `has_safety_check`, `supported_by_source`를 구분한다. 증상과 질환의 연관을 확정적 인과관계나 충분조건으로 저장하지 않는다.

모든 임상 관계에는 출처·문서 버전·대상 환자군·적용 조건·검토 상태를 둔다. 통계 근거가 없는 관계에 임의 확률을 부여하지 않는다. SNOMED CT 같은 표준 용어는 개념 식별과 계층에 활용하고, 진단·치료 판단 규칙은 지침과 별도로 관리한다. SNOMED의 CDS 문서도 추론 엔진이 기록·용어·규칙·지침을 함께 사용한다고 설명한다. [SNOMED CDS 추론 엔진](https://docs.snomed.org/snomed-ct-practical-guides/snomed-ct-clinical-decision-support-guide/4-inference-engine)

### 3.2 환자 사실의 최소 스키마

| 필드 | 의미 |
| --- | --- |
| concept_id, surface_text | 내부 개념 ID와 원문 표현 |
| subject | 환자 본인·가족·기타 주체 |
| assertion | present / absent / uncertain / unknown |
| temporality | 현재·과거·기간·발병 시점·변화 |
| value, unit, qualifier | 수치·단위·부위·강도·빈도 |
| source_type, source_turn, source_span | 시작 정보·SAY·EXAM·TEST, 턴, 원문 위치 |
| extraction_confidence | 추출 신뢰도. 질환 확률과 구별 |
| verification_state | 확정 추출·검토 필요·상충 |

`not_asked`·`asked_unanswered`는 정보수집 진행 상태로 따로 둔다. “질문했다”와 “답을 얻었다”를 분리하기 위해서다. 음성이 기록에 없다는 이유로 양성으로 보거나, 정보가 없다는 이유로 정상으로 보지 않는다. 같은 항목의 상반된 답은 시간 변화인지 실제 모순인지 확인하고 둘 다 보존한다.

약물은 성분/제품명·제형·1정 용량·1회 정수·횟수·시점·처방 복용과 실제 복용을 구분한다. 총량 계산은 단위와 기간이 확인된 경우에만 수행한다. “가끔”을 “주 1회”처럼 임의 정량화하지 않는다. 동의어 후보가 여러 개인 경우 원문과 후보를 유지하며 성급히 하나로 확정하지 않는다.

### 3.3 구축 범위와 표준 매핑

첫 배포 범위는 검토 가능한 일반 초진 주호소군 약 10개, 핵심 개념 약 300–500개, 문진·진찰·설명 템플릿 약 80–120개를 초기 상한으로 잡는다. 이는 검증된 전체 질환 목록이 아니며 예선 평가 질환의 분포를 추정한 숫자도 아니다. 실제 지침과 검토 속도를 보고 줄일 수 있다. 범위 밖 증례는 일반 초진 프레임과 검색으로 처리한다.

초기 내부 ID는 `nova:symptom/...`처럼 독립적으로 만든다. SNOMED CT·UMLS 등의 매핑은 사용 권한·버전·동일성 검토가 완료된 부분부터 붙인다. 유사한 개념을 모두 exact match로 묶지 않는다. UMLS는 여러 생의학 용어를 통합하지만 접근·사용에는 라이선스와 원천 용어 조건 확인이 필요하다. 전량 도입을 예선 일정의 선행 조건으로 두지 않는다. [NLM UMLS](https://www.nlm.nih.gov/research/umls/index.html)

구축 단계는 개념 목록 → 한영 동의어·환자 표현 → 관계 후보 → 출처 연결 → 임상 검토 → 구조 검증 → 릴리스다. LLM이 뽑은 관계는 자동으로 승인하지 않는다. 검토 인력이 없으면 미검증 치료·배제 규칙은 활성화하지 않고 근거 검색 자료로만 쓴다.

## 4. 데이터·검색 구현

### 4.1 두 지식 영역

대회 계약 지식은 턴·오류·필드·모델·평가 기준을 다루고, 임상 지식은 질환·증상·진찰·계획을 다룬다. 운영 문서가 임상 사실로 검색되거나 환자 답변이 실행 지시가 되지 않도록 자료 유형과 신뢰 경계를 유지한다.

대회가 제공하는 임상 자료는 런타임 `NOVA_GUIDELINES_DIR`에서 읽는다. 문서별 출처·라이선스·버전을 기록하며, 번역·요약·재구성본의 배포가 제한된 자료는 파생 온톨로지·요약을 제출 자산으로 넣을 수 있는지 별도로 확인한다. 허용되는 원문 참조·검색과 파생 자산 배포를 구분하고, 불명확하면 해당 파생물의 패키징을 보류한다. [공식 개발 가이드 자료실](https://nova.snubhai.org/docs/#guidelines)

### 4.2 검색 단계

1. 주호소·양성/음성 소견·기간·약물·위험 인자를 검색 질의로 만든다.
2. 동의어와 영문 표준 표현을 추가하되 부정·주체·시간은 별도 필터/특성으로 유지한다.
3. BM25 또는 표준 라이브러리 기반 역색인과 그래프 인접 관계로 후보를 찾는다.
4. 질환명 일치만으로 순위를 정하지 않고 현재 환자군·핵심 구분 소견·지침 버전으로 정렬한다.
5. 우선 3–5개 근거 단락을 반환한다. document_id·section·원문 위치·적용 조건을 붙인다.

벡터 검색은 2차 옵션이다. 어휘 검색에서 한국어 구어체·영문 용어 대응이 부족한지 먼저 측정한다. 임베딩 모델·가중치·인덱스까지 코드 ZIP 50MB와 RAM 제한 안에 들어가는지 검증하고, 이득이 있을 때만 추가한다. 문서 전체를 준비 단계마다 전수 임베딩하지 않는다. 사전 색인·메타데이터를 압축해 포함할 수 있는지 확인하고, 제한을 넘으면 주호소별 후보 파일을 좁혀 필요한 부분만 읽는다.

초기 예산안은 코드·스키마·프롬프트 5MB, 사전·그래프·템플릿 10MB, 검색 메타데이터·색인 20MB, 여유 10MB로 총 ZIP 45MB 이하다. 실제 압축·해제 크기·파일 수와 준비 시간을 측정한 뒤 조정한다. RAM 피크 6GB 이하·준비 2분 이내를 내부 여유 목표로 두되 아직 실측값은 아니다.

## 5. 진료 제어와 프롬프트

### 5.1 단계 기반 제어

| 단계 | 진입·종료 조건 | 주요 행동 |
| --- | --- | --- |
| 초기 분류 | 시작 정보 수신 | 주호소·활력징후·즉시 확인할 위험 요인 파악 |
| 핵심 문진 | 주요 증상 구조가 미완성 | 발병·기간·경과·관련 증상·약물·병력 확인 |
| 감별 구분 | 복수 가설이 남음 | 결정에 영향을 주는 추가 질문·구체적 진찰 |
| 계획 수립 | 처치 결정에 필요한 근거 확보 | 추가 검사·치료 방향·추적·안전 계획 |
| 설명·확인 | 제출 전 | 짧은 SAY로 판단·계획·경고 증상·필요한 공감 전달 |
| 기록·제출 | 필수 근거 확보 또는 종료 예산 도달 | SOAP·주진단 검증과 제출 |

고정 턴 수만으로 종료하지 않는다. 초기에는 일반 정보수집 5–10턴, 집중 문진·진찰 15–25턴, 설명 3–6턴을 참고 범위로 잡고 증례별 조정한다. 50턴을 다 쓰는 것이 목표가 아니다. 남은 시간·턴·모델 출력 예산이 부족하면 안전과 제출을 우선한다. 설명할 턴을 초반부터 예약하며 기록 생성 시간을 남긴다.

### 5.2 행동 선택

후보 행동마다 다음 값으로 우선순위를 매긴다.

`행동 가치 = 감별 구분 기여 + 안전상 필요 + 필수 정보 보완 + 설명 필요 − 중복 − 예상 시간·토큰·턴 비용`

처음에는 이 식을 설명 가능한 휴리스틱으로 구현한다. 검증되지 않은 LLM 확신을 진단 확률이나 계산된 정보이득으로 부르지 않는다. 실제 정보이득 최적화는 확률 모델과 검증 자료가 확보된 뒤 검토한다. 위험 요인이 해결되지 않으면 일반 질문의 높은 점수보다 먼저 확인한다. 검사를 예선 EXAM으로 우회하지 않는다.

### 5.3 프롬프트 구성

고정 지시에는 역할·허용 행동·30자·단일 질문·사실과 계획 구분·출력 JSON 계약을 둔다. 매 턴에는 확정 사실, 미확인 필수 항목, 상충 사실, 상위 3–5개 가설, 아직 확인할 구분 소견, 근거 단락, 수행한 행동, 잔여 예산을 전달한다.

첫 버전의 Planner 출력 예시는 다음과 같다. 이 JSON은 하네스 내부 형식이며 대회 API에 그대로 보내는 형식은 아니다.

```json
{
  "state_updates": [],
  "hypotheses": [
    {"concept_id": "nova:disease/example", "support_fact_ids": [], "opposing_fact_ids": [], "missing_fact_ids": []}
  ],
  "next_action": {"type": "SAY", "content": "복용 중인 약 이름이 뭔가요?", "purpose": "medication_identity"},
  "finish_ready": false
}
```

최종 기록 프롬프트에는 실제 근거 사실 ID와 내용, 판단 근거, 실행할 계획만 제공한다. 검증기는 환자 나이·단위·복용량·양성/음성·진찰 턴·주진단 일관성을 대조한다. 기록의 각 주장에 근거가 연결되어야 하며 계획을 이미 시행한 것으로 바꾸지 않는다.

별도의 Critic 호출은 모순, 안전상 중요한 정보 누락, 근거 없는 진단 전환이 있을 때만 발동한다. 통상 행동 선택은 low/medium을 비교하고, 복잡한 감별·최종 기록에만 필요 시 추론 수준을 높인다. `temperature`의 효과는 현재 문서가 모순되므로 기본값 생략을 출발점으로 한다. 추론 전문 대신 짧은 사실 ID와 선택 목적을 남겨 비용을 통제한다.

## 6. 평가 항목별 개선·측정 계획

공식 배점은 정보수집 25, 진단추론 15, 검사·추적 10, 안전 15, 의사소통 15, 효율 20이다. 아래 지표는 개발용 대리지표이며 비공개 공식 채점식을 재현한다고 보지 않는다. [공식 평가](https://nova.snubhai.org/evaluation/)

| 항목 | 구현 장치 | 개발 시 측정할 지표 |
| --- | --- | --- |
| 정보수집 25 | 주호소별 필수 항목, 확인 상태, 약물·병력 구조, 필요한 진찰 후보 | 필요한 정보 획득률, 획득 사실의 기록 반영률, 중복·거절 비율 |
| 진단추론 15 | 지지·반대 근거, 핵심 구분 소견, 조기 진단 확정 방지 | 주진단 일치, 감별 후보 포함률, 근거 없는 판단 비율 |
| 검사·추적 10 | 근거와 연결된 추가 검사·재진·경고 증상 슬롯 | 적절성 검토 통과율, 계획 누락률, 불필요한 검사 제안 |
| 안전 15 | 위험 신호·알레르기·실제 복용량·처치 결정 확인 | 중요한 위험 정보 누락, 근거 없는 처치 제안, 안전 시나리오 실패 |
| 의사소통 15 | 공감·중간 요약·판단·계획·안전 설명 상태 | 실제 SAY에서 설명한 내용의 충족률, 질문 하나 원칙 준수 |
| 효율 20 | 중복 차단, 선택적 검색·검토 호출, 압축 상태, 종료 조건 | 턴·Doctor 호출·출력 토큰·소요시간·비용, 영역 점수와의 균형 |

의사소통은 교육 문장을 P에 넣는 것만으로 충족되지 않는다. SAY로 실제 전달해야 한다. 검사·추적은 예선 TEST가 없어도 P에 계획과 이유를 작성한다. 긴 형식적인 SOAP보다 실제 확보한 핵심 사실과 적절한 계획을 우선한다.

## 7. 검증 설계와 채택 기준

### 7.1 비교 실험

| 실험군 | 구성 | 확인 목적 |
| --- | --- | --- |
| A | 시작 패키지 기본 에이전트 | 동일 모델의 기준 성능 |
| B | A + 프로토콜·증거 ledger·기록 검증 | 실행·기록 개선분 |
| C | B + 경량 온톨로지·상태 기반 Planner | 의미 정규화·질문 선택 개선분 |
| D | C + 어휘/그래프 검색 | 지침 검색 추가 효과 |
| E | D + 선택적 검토·프롬프트 개선 | 추가 호출 대비 품질·비용 |
| F, 선택 | E + 벡터 검색 | 어휘 검색 대비 독립적 추가 이득 |

실험 순서는 누적 개선을 빠르게 확인하기 위한 것이다. 후보 선정 후 온톨로지만 제거·검색만 제거·검토 호출만 제거하는 실험으로 개별 기여도도 확인한다. 같은 증례·동일 Doctor·동일 예산으로 비교하고 실행 변동을 기록한다. 모델의 비결정성을 고려해 주요 후보는 증례당 3회 반복을 목표로 하되 비용에 따라 축소한다.

개발 세트는 공개 샘플 3건과 별도 합성·허용된 공개 증례를 사용한다. 초기 30–50건을 목표로 하되 수작업 검토 가능량을 우선한다. 질환·증례 템플릿·출처가 겹치지 않도록 개발/검증을 나누고, 문장만 바꾼 같은 증례가 양쪽에 들어가지 않게 한다. 공개 샘플 원문 대본·정답은 평가 전용으로 격리하며 런타임 검색이나 프롬프트에 싣지 않는다. 공개 예시에 맞춘 진단 하드코딩을 하지 않는다.

외부 벤치마크는 문진·추론·기록 등 맞는 하위 과제를 평가하는 데 사용하고 NOVA 형식과 다른 점을 보고한다. 자가채점은 판정 근거를 보이게 하고, 가능하면 일부를 임상 검토자가 독립 검토한다. LLM 채점에는 선택된 진단·원본 사실·허용된 정답 기준만 주고 에이전트 버전명을 숨겨 편향을 줄인다. 합성 증례의 정답 자체 오류도 별도 검수한다.

### 7.2 초기 통과 목표

- 고정 회귀 세트에서 제출 성공 100%, 필드·문자 수·잘못된 단계 행동 위반 0건.
- 근거 없는 음성 소견·나이/용량 변경은 사람이 검토한 회귀 세트에서 0건을 목표로 한다. 자동 검사 통과만으로 달성을 주장하지 않는다.
- 중요한 안전 실패가 증가한 후보는 총점이 높아도 채택하지 않는다.
- 주진단 일치·정보수집·기록 충실도 개선이 반복에서 유지되는지 확인한다.
- 같은 품질이면 호출·토큰·시간이 적은 후보를 선택한다. 품질을 올리는 추가 비용은 영역별 변화와 함께 보고한다.
- 표본이 작으면 점수 평균만으로 우열을 단정하지 않고 증례별 차이·실패 유형·변동 범위를 함께 제시한다.

기록 검증은 JSON/Python으로 먼저 구현한다. 온톨로지의 타입·출처·허용 관계 검증에는 빌드 단계 SHACL을 선택적으로 사용한다. SHACL은 RDF 그래프 제약 검증용이며 진단의 의학적 타당성을 자동 보증하지 않는다. [W3C SHACL](https://www.w3.org/TR/shacl/)

## 8. 구현 일정과 산출물

아래는 예선 집중 개발을 위한 약 4–5일의 작업 배분 추정이다. 인력·기존 코드·임상 검토 가능량에 따라 달라지며 공식 마감 시각은 별도로 확인한다. 각 단계의 통과 조건을 만족하면 제출 가능한 버전을 남긴다.

| 단계 | 작업량 추정 | 산출물·완료 조건 |
| --- | --- | --- |
| 0. 실행 기준선 | 0.5일 | 최신 SDK 계약 확인, baseline 로그, 로컬 Docker 재현, 정상 제출 |
| 1. 증거·기록 | 1일 | 사실 스키마·추출·숫자/부정 검증, SOAP 생성, 오류 회귀 세트 |
| 2. 핵심 온톨로지·Planner | 1일 | 검토된 개념·관계, 필수 질문/설명 슬롯, 적응형 종료 |
| 3. 근거 검색·프롬프트 | 1일 | CPU 어휘 검색, 근거 연결, 역할별 프롬프트, 선택적 검토 |
| 4. 비교·패키징 | 1일 | A–E 비교, 후보 선정, ZIP·RAM·시간 확인, 서버 샘플 검증 |

시간이 부족하면 단계 0–2를 우선 완료하고 검색은 작은 검토 자료 범위로 제한한다. 벡터 검색·전체 표준 용어 통합·학습 기반 행동 최적화는 실측 필요성이 입증된 뒤 진행한다. 본선에서는 같은 스키마·Planner·검증기를 유지하면서 모델 어댑터를 로컬 모델로 바꾸고 TEST 흐름·GPU 예산을 추가 검증한다.

예정 산출물은 `agent/` 모듈, `ontology/`의 스키마·개념·관계·출처표, `prompts/`의 버전별 지시문, `eval/`의 회귀·비교 설정, `reports/`의 증례별 결과다. 정적 지식과 환자별 로그를 분리하고 다른 증례 상태는 다음 실행으로 넘기지 않는다.

## 9. 최종 권고

첫 구현 목표는 거대한 의료 지식 그래프가 아니라 **출처를 보존하는 환자 상태, 검토된 작은 온톨로지, 누락을 찾는 진료 정책, 사실에 맞는 SOAP 제출**이다. 이것을 정상 실행되는 기준 버전에 먼저 연결하고, 검색·프롬프트의 점수 기여를 따로 측정해 확대한다. 기대 점수는 baseline 측정 전 제시하지 않으며, 모든 개선 주장은 증례별 비교 결과로 보고한다.
