# NOVA 새 에이전트 의사결정 기록

최종 갱신: 2026-10-20 KST. 이 문서는 사용자와의 대화에서 확인한 목적·고민·선택·실험 결과를 이어서 기록하는 프로젝트 기억이다. 전체 대화의 축어록은 아니며 키·인증정보·원문 진료 로그는 넣지 않는다. 사용자 발언의 요지와 개발자의 판단을 구분한다.

## 현재 방향과 목표

**사용자 의도:** 기존 MedDB 프로젝트의 점수가 잘 오르지 않아 별도의 새 에이전트를 함께 개발한다. MedDB 분석은 유용한 부분을 재사용하기 위한 것이며, 새 프로젝트를 기존 E2의 패치 작업으로 한정하려는 의도가 아니다.

| 단계 | 목표 | 달성 판단 |
| --- | --- | --- |
| 1차 | 공식 점수 ≥78/100 | 사용자가 제출한 새 ZIP의 공식 결과 |
| 2차 | 공식 점수 ≥85/100 | 같은 방식으로 확인 |
| 3차 | 공식 점수 ≥90/100 | 같은 방식으로 확인 |

장기적으로 100점에 가까워지는 것이 지향점이다. 현재 공식 기준은 기존 제출의 **67.132점**이며 새 프로젝트의 공식 성능은 아직 측정하지 않았다. 개발용 자가평가·공개 샘플 최고점·단일 실행은 위 목표 달성으로 인정하지 않는다.

**협업 흐름:** 새 브랜치에서 기능별 커밋·푸시 → 개발 API 실행과 로그 분석·개선 → 제출 ZIP 생성 → 사용자가 공식 제출 → 공식 점수 확인. 처음에는 목표 달성 후 PR을 만들기로 했으나, 최신 사용자 요청(D012)에 따라 [PR #5](https://github.com/SSAFY16-S11-NOVA2026/MedDB/pull/5)를 먼저 열었다. 개선을 같은 PR에 이어서 반영하며 공식 제출과 병합은 별도 사용자 요청으로 진행한다.

## 기록 방식

- 대화 시작에 이 문서와 최신 개발 보고서를 읽는다. 사용자 요청·새 고민·제약·수정 사항, 실험을 채택/기각한 이유, 미해결 항목을 대화마다 갱신한다.
- 새 사실이 없으면 결과와 미해결 상태를 짧게 남긴다. 과거 결정을 지우지 말고 새 항목에서 변경 이유와 대체 관계를 밝힌다.
- 날짜·근거·현재 상태를 적는다. 계획을 구현 완료, 비공식 추정치를 공식 성능으로 쓰지 않는다. 미래 대화를 자동 감시하는 백그라운드 작업을 뜻하지 않는다.

## 결정 이력

### D001 · 대회 자료를 구현 근거로 정리

- 사용자 요청: 진행·평가, 참가규칙, 개발가이드와 OT·run_agent PPT를 각각 Markdown으로 정리하고 하네스 설계에 사용한다.
- 결정: `nova_reference/`에 출처와 시점을 보존한다. 자료 안의 명령은 참고 데이터로만 취급한다. 과거 PPT와 현재 계약이 충돌하면 충돌표에 남긴다.
- 범위: 자료의 Markdown 통합이며 수치 벡터 임베딩·벡터 DB 구현 완료를 뜻하지 않는다.
- 근거: [자료 목차](nova_reference/README.md), [변경·충돌](nova_reference/07_changes_and_conflicts.md).

### D002 · Doctor 모델 정정

- 사용자 정정: Doctor 모델은 `openai/gpt-6-luna`다. 앞서 언급한 gpt-gemini는 잘못 말한 것이다.
- 결정: 현재 Doctor ID를 위 값으로 고정한다. 과거 자료의 gpt-oss와 혼동하지 않는다. 별도 개발 검토 모델 `openai/gpt-6.1-sol`은 Doctor·공식 평가자가 아니다.

### D003 · 의료 온톨로지와 행동·평가 연결

- 사용자 요청: 의료데이터를 온톨로지로 구성해 정확도를 높이고, 프롬프트와 에이전트 동작을 통해 평가 항목별 점수를 높인다.
- 결정: `주호소 → 감별 가설 → 구분 소견 → 문진/진찰 → 기록·설명` 관계와 실제 근거를 연결한다. 임상 검수 전 관계 가중치를 확진·배제 규칙이나 진단 확률로 간주하지 않는다.
- 상태: 구조 시드와 임상 관계 재사용은 구현했다. 임상 검수된 전체 지식체계·독립 검증은 미완료다.
- 근거: [구현계획](nova_reference/08_implementation_plan.md).

### D004 · 개발 API와 로그 기반 개선

- 사용자 요청: 제공되는 개발 API로 모델을 실행하고, 결과 로그에서 어디서 문제가 생겼는지 분석해 해결책을 검토하며 개선한다.
- 결정: 실행별 설정·코드 해시·요청/응답·오류·사용량·기록을 남기고 비교한다. 공개 대본·모범 기록은 별도 평가 도구에서만 사용하고 진료 런타임에는 주입하지 않는다.
- 보안: 사용자가 로컬 `.env`에 키를 설정했다. 키 값과 `.env`, 원문 실행 결과는 Git·제출 ZIP에서 제외한다. API를 새 모델 실행에 사용하는 기존 승인은 유효하되 무의미한 반복 유료 실행은 피한다.

### D005 · 초기 하네스의 한계 인정

- 관찰: C01 초기 하네스는 개발용 추정 37→36→44점, 비교 baseline은 40점이었다. C10은 baseline 63/하네스 66, C03은 58/53이었다.
- 결정: 형식 준수·원문 보존·속도만으로 진료 품질 개선을 주장하지 않는다. 정보수집·감별·실제 설명 부족을 다음 개선 대상으로 삼는다.
- 근거: [1차 보고](reports/development_001.md), [2차 보고](reports/development_002.md). 모두 비공식 단일 실행이다.

### D006 · 종료 Critic 기본 비활성화

- 관찰: 종료 전 검토를 추가한 C01은 추정 36점으로 개선되지 않았고, 긴급 종료 판단으로 추가 문진을 하지 않았다.
- 결정: `closure_audit`는 기본 비활성화하고 선택적 실험으로 보존한다. 복잡한 검토 호출이 자동으로 성능을 높인다고 가정하지 않는다.

### D007 · MedDB 공식 결과를 기준점으로 보존

- 사용자 공유: 기존 MedDB 저장소와 공식 결과 캡처. `submission_E2_hybrid_care.zip`은 67.132점이며 5증례가 정상 종료했다.
- 영역: 정보수집 12.90/25, 추론 12.00/15, 검사·추적 6.75/10, 안전 15.00/15, 의사소통 7.10/15, 효율 13.38/20.
- 결정: 정보수집·의사소통의 손실을 우선 다루되 안전을 유지한다. 공식 원본 ZIP이 없으므로 Git 커밋과 캡처 제출물이 동일하다고 주장하지 않는다.
- 근거: [공식 기준 메타데이터](reports/official_reference.json), [MedDB 분석](reports/meddb_review_003.md).

### D008 · MedDB를 참고 자산으로 재사용

- 결정: 고정 커밋 `63743a8b8a2e278b426d18fc040e880740318ae3`의 주호소 19개·질환 134개·소견 289개·진찰 56개·문진 슬롯 19개를 경량 구조로 가져왔다. 출처와 해시를 보존한다.
- 상태: 새 하네스의 임상 행동 후보, 근거 추적, 실제 EXAM 기반 징후 반영에 사용한다. 대형 그래프·정답·채점 체크리스트·치료 자동 실행 규칙은 경량 런타임에 가져오지 않는다.
- 참고: 원본 E2를 보존한 확장도 비교 실험으로 만들었으며 새 프로젝트의 최종 구조를 E2로 결정한 것은 아니다.

### D009 · 설명 생성과 실제 전달을 구분

- 관찰: 초기 통합 후보는 30자 초과로 종료 설명 5개가 모두 빠졌다.
- 결정: 길이 수리·완결 문장 선택, 실제 SAY 추적, 걱정 확인·이해 확인을 추가했다. 전송하지 않은 문장을 설명 완료로 처리하지 않는다.
- 남은 문제: 길이를 맞춰도 내용이 충분하지 않았고, 환자 질문에 답하지 않거나 안전 설명이 빠졌다. 계획과 실제 수행의 기록 분리도 더 필요하다.

### D010 · 최신 후보를 성능 검증 완료로 채택하지 않음

- 2026-10-18 실험: C01 원본 E2 65, 초기 통합 44, 설명 수리 통합 62, E2 확장 62. C03 통합 60/압축 61, C10 통합 70. 전부 비공식 자가평가이며 각 조건 1회다.
- 결정: 원본보다 전반적 우수성이 입증되지 않았다. 공식 제출 교체를 권하지 않고 코드·실패 근거를 보존한다. 새 하네스는 계속 개선할 실험 프로젝트다.
- 현재 검증: 프로젝트 49개·원본 관련 11개 테스트 통과. Docker 및 최종 ZIP 공식 서버 검증은 미완료다.
- 근거: [3차 보고](reports/meddb_review_003.md), [실험 표](reports/meddb_benchmark_003.md).

### D011 · 새 프로젝트라는 사용자 의도와 단계 목표 확정

- 사용자 고민: 기존에 만들던 프로젝트의 점수가 잘 오르지 않아 지금의 새 프로젝트를 함께 개발 중이다.
- 사용자 요청: MedDB에 새 브랜치를 만들고 현재 작업을 기능별 커밋·푸시한다. 대화·고민·결정을 Markdown으로 남기고 매 대화 갱신한다. 목표는 순서대로 공식 ≥78, ≥85, ≥90점이다. 목표 달성 후 PR을 진행할 예정이다.
- 결정: 새 브랜치는 `codex/nova-harness-rebuild`. 새 프로젝트는 브랜치의 `nova_harness/`에 독립 진입점·모듈·테스트·도구·자료·보고서로 보관한다. 원본 MedDB 루트를 덮어쓰지 않고 main도 변경하지 않는다.
- 이유: 새 설계를 독립적으로 발전시키면서 원본과 비교·재사용할 수 있고, 기존 제출 경로의 회귀를 피할 수 있다. 같은 저장소 사용은 기존 구조를 유지해야 한다는 제약이 아니다.
- 이번 범위: 구현 기능별 커밋 및 브랜치 푸시. 제출 ZIP·키·원문 실행 로그는 푸시하지 않는다. PR은 만들지 않는다.
- 실행 결과: 기능별 커밋 7개를 푸시하고 원격 브랜치가 `0891a8ca3336f93425fc4686984f5533839bad8a`를 가리키는 것을 확인했다. main은 기준 커밋 그대로였다. 게시본에서는 테스트 49개 중 선택 의존성 없는 48개가 통과하고 E2 overlay 1개를 건너뛰었다. 의존성이 있는 기존 개발 폴더의 49개 전체 통과와 구분한다. 이후 전달 검증 문서를 별도 커밋으로 남긴다.
- 재현성: 로컬 게시용 checkout은 `vendor/meddb-publish/`, 실험 비교용 원본은 `vendor/meddb/`로 분리했다. 후자는 고정 커밋으로 유지하여 기존 임포트·비교 실험의 전제가 바뀌지 않게 한다.

### D012 · PR을 먼저 만들고 개선 지속

- 사용자 변경 요청: PR 제목·본문을 작성해 지금 PR을 열고 계속 개선한다. 목표 달성 후 PR을 만들려던 D011의 보류 조건을 대체한다. 공식 점수 목표는 변경하지 않았다.
- 실행: [PR #5](https://github.com/SSAFY16-S11-NOVA2026/MedDB/pull/5), 제목 `feat: NOVA 독립 에이전트 하네스와 로그 기반 개선 체계 구축`. 구현·측정 한계·미달성 상태를 본문에 명시했다. 병합·공식 제출은 하지 않았다.
- 이번 개선 가설: 한 목적을 30자 한 문장에 압축하면 내용이 빠진다. 여러 짧은 완결 문장, 중간 환자 질문 응답, 실제 SAY와 계획의 기록 분리로 이를 줄인다.
- 구현: v0.4.0 종료 설명 배열, 항목별 최대 3문장, 환자 질문에 최대 2회 응답 생성, 이해 확인 후 1회 교정, 성공한 SAY 출처 기반 교육 기록, 종료 누락·전송 계측. 종료 예약은 8→12턴으로 변경했다.
- 검증: v0.4.0 C01·C10을 각각 한 번 실행해 정상 종료했다. 비공식 추정은 C01 45점(이전 v0.3.2 62), C10 67점(이전 v0.3.0 70)이다. 의사소통 추정은 각각 7→9, 6→9였지만 전체 성능은 개선되지 않았다. 공식 제출 후보로 채택하지 않는다.
- 후속 수정: 실제 C10에서 발견한 불완전 연결절을 거절하고, 종료 단계도 최대 12턴으로 제한한 v0.4.1을 만들었다. 테스트 60개 통과. v0.4.1 개발 API 재측정은 아직 하지 않았으며 v0.4.0 점수를 이 버전의 성적으로 쓰지 않는다.
- 근거: [4차 보고](reports/development_004.md), [비교 표](reports/benchmark_004.md). PR 생성·기능 수정·공식 목표 달성을 구분한다.

### D013 · 설명 튜닝보다 핵심 수집·근거 검증을 다음 우선순위로

- 관찰: C01은 핵심 병력을 묻지 않고 급성 위험 대응을 반복했으며, 부분 답변을 호흡 상태까지 확인한 것으로 기록했다. C10은 설명·답변에 많은 턴을 써 효율이 낮아졌다.
- 결정: 설명 전송 기능과 기록 분리는 유지할 실험 기반으로 두되, 이를 성능 향상으로 채택하지 않는다. 다음 유료 비교 실행 전에는 주호소별 미해결 관찰, DONE 조건, A/P의 실제 응답 출처·불확실성 검증을 우선 구현한다.
- 이유: 의사소통의 국소적 추정 상승이 정보수집·추론의 큰 손실을 상쇄하지 못했다. 정답·증례 ID를 주입하거나 응급 대응을 무조건 억제하는 방식으로 해결하지 않는다.
- 상태: 위의 수집·근거 검증 개선은 다음 작업이며 구현 완료가 아니다. 공식 목표는 여전히 미달성이다.

### D014 · 개발 API 기준 측정 후 수집·근거 검증 개선

## 2026-10-20 핵심 진료 원리 확인 (D050)

- 사용자 확인: 환자의 실제 응답과 실제 진찰 결과를 관찰근거로 축적하고, 의료지식과 현재 관찰근거를 함께 고려해 다음 행동을 선택한다. 행동 결과를 다시 관찰근거로 넣어 순환하며, 제한된 턴 안에 SOAP과 진단을 완성하는 것이 핵심 원리다.
- 순서 보정: SOAP을 먼저 확정한 뒤 별도로 진단하는 구조가 아니다. 누적 관찰근거를 바탕으로 최종 진단·감별·계획을 함께 결정하고 그 결정을 SOAP에 근거와 함께 표현한 뒤, 진단명과 SOAP을 `diagnose()`로 함께 제출한다.
- 의료지식은 행동 후보와 해석을 돕지만 환자에게서 관찰된 사실을 대신하지 않는다. 질문하지 않은 정보와 시행하지 않은 진찰·검사는 관찰근거나 완료 사실로 기록하지 않는다.

## 2026-10-20 반복 대화 중 SOAP 근거 소실 위험 확인 (D051)

- 사용자 우려: 대화를 반복하면서 초기에 얻은 SOAP용 정보가 문맥에서 밀리거나 최종 기록에서 누락될 수 있다.
- 판단: 실제 위험이다. 모델 프롬프트의 최근 대화 절단, 자유응답의 target/fact 매핑 실패, 최종 기록 모델의 선택적 요약, 기록 이후 마무리 대화에서 생긴 새 정보의 재기록 조건이 주요 소실 경로다.
- 신형 하네스는 모든 성공 SAY/EXAM을 `PatientState.evidence`에 원문·턴·target과 함께 누적하고, SOAP S/O를 코드가 전체 evidence에서 다시 렌더링한다. 최종 모델이 `history_routes`를 빠뜨려도 SAY 응답은 HPI fallback으로 보존하고 모든 EXAM은 O에 포함한다. 필드 크기 제한으로 생략할 때는 생략 표시를 남긴다.
- E2 경로는 Planner에 최근 60줄만 보이지만 `Tracker.answers`, present/absent, turns, `CareCoverage.records`와 전체 transcript를 최종 기록 입력에 사용한다. 다만 자유응답이 구조화 상태에 연결되지 않거나 기록 모델이 요약에서 빼는 경우, 마무리 답변이 KB fact를 바꾸지 않아 재기록 조건이 작동하지 않는 경우에는 누락 가능성이 신형 하네스보다 크다.
- 다음 구조 우선순위: E2에 프롬프트를 더 붙이기보다, 성공한 모든 SAY/EXAM의 불변 evidence ledger와 코드 기반 S/O 렌더링을 얇게 이식하고 SOAP 제출 전 `전체 evidence ID → SOAP 반영/의도적 제외 사유` 감사를 수행한다.

## 2026-10-20 Evidence Ledger 구현 계획 확정 (D052)

- 사용자 요청: 반복 대화 중 SOAP 근거 소실을 해결할 구체적 구현사항을 보고한다.
- 결정: 원본 E2의 진료 행동·진단을 동시에 바꾸지 않고 `tracking client → append-only ledger → 결정론적 SOAP router → 제출 직전 completeness audit`를 얇은 가역 오버레이로 구현한다.
- 모든 근거를 SOAP에 무조건 넣지 않는다. 각 항목은 반영, 중복, 비임상, 대체, 상충, 사유 있는 제외 중 하나로 처리하며 중요한 임상정보의 무사유 누락을 금지한다.
- 검증은 고정 fixture, 합성 45턴, 개발 API C01/C03/C10, 공식 샘플 순서다. 원본 대비 추가 환자 턴과 Doctor 호출 0을 목표로 하고 안전 15 및 효율 19.42 회귀 시 폐기한다.
- 상세 설계: [20차 구현 계획](reports/implementation_plan_020.md). 이번 회차는 계획 보고이며 런타임 구현·API 실행은 하지 않았다.

## 2026-10-20 Evidence Ledger 구현·3증례 구조 검증 (D053)

- 사용자 승인: D052의 구현 계획대로 개발과 검증을 진행한다.
- 구현: 성공 SAY/EXAM append-only ledger, tracking client, 결정론적 SOAP router, completeness audit, 가역 overlay를 추가했다. 원본 E2의 질문·진찰·진단 정책은 바꾸지 않는 ledger-only 실험이다.
- 개발 API: C01 45턴, C03 33턴, C10 44턴으로 정상 종료했고 각각 수면제 의존, 체질성 성장지연, 그레이브스병으로 진단했다. 총 122개 관찰근거의 포착·처리율은 100%, unresolved·중요 EXAM 무사유 제외는 0건이다.
- 로그 반영: 설명 뒤 실제 환자 질문을 단순 수용으로 제외하던 오분류와 안전 이행 확인을 HPI에 넣던 오분류를 고쳤다. 실제 SAY가 없는 교육 문구는 수행 완료가 아닌 `실제 전달 여부 미확인 계획`으로 분리했다.
- 검증: 171개 테스트가 통과했고 저장된 세 API 실행을 최종 라우터로 오프라인 재생해 교육 계획/전달 미분리 0건을 확인했다. `compileall`은 macOS Python의 작업공간 밖 캐시 쓰기 권한으로 실패했으나, 단위 테스트가 변경 모듈을 import·실행했다.
- 판단: 구조 검증은 통과했지만 공식 점수 향상은 미확인이다. SOAP 길이 증가가 효율·소통 평가에 미치는 영향과 원본 E2 안전 15·효율 19.42 보존은 공식 샘플로 확인해야 한다. 현재 제출 권장 후보나 ZIP으로 승격하지 않는다.
